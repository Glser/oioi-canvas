OIOI / SYSTEM DESIGN NOTE 01
结论拓扑API 接入部署落地
flow.oioi.lat / 独立运营架构

把画布放在
边缘入口，把能力留在 API。

本方案将画布视为一个纯前端、浏览器本地持久化的创作工作台；澳洲云服务器负责公网入口、TLS 与反向代理，国内火山云负责 API/源站能力。这样既保留现有项目的前端形态，也为后续独立运营、域名切换和 API 复用留下清晰边界。

推荐基线

生产环境优先让澳洲节点成为唯一公网入口；国内节点不直接暴露业务端口。静态前端可以先走反代，稳定后建议改为构建产物同步到澳洲节点本地服务。

01 / DECISION

先给结论

你的方向是可行的，但建议把“静态资源反代”和“API 统一入口”明确拆开，避免后续所有流量都被绑在一个 nginx location 上。

RECOMMENDED

澳洲边缘入口 + 国内 API 源站 + 浏览器本地数据

对外只公布 flow.oioi.lat 和 api.oioi.lat。两个域名都解析到澳洲云服务器，由澳洲 Nginx 终止 HTTPS，再通过 WireGuard 私网隧道或固定 IP 白名单访问火山云上的源站。画布页面直接调用 api.oioi.lat 的登录、模型列表和模型调用接口；画布节点、素材索引与生成记录继续存储在浏览器 IndexedDB/localforage，不进入服务端数据库。

最小改造保留现有前端路由与本地数据模型，只新增 API 地址配置和跨域/认证适配。
更好的网络边界公网只看到澳洲入口；国内源站只接受边缘节点或隧道网段的流量。
可平滑演进未来可以将静态文件迁到澳洲节点，而 API、任务队列和模型供应商仍留在国内。
02 / TOPOLOGY

建议的系统拓扑

这里将“访问入口、业务 API、浏览器数据”分别放在不同边界上，后续排障时可以快速判断是边缘、链路、API 还是浏览器本地存储的问题。

图中“浏览器本地数据层”不经过澳洲或国内服务器；服务端只负责认证、模型目录、模型调用和必要的任务状态。
03 / HOSTING CHOICE

反代方案 vs. 更优静态部署

你提出的澳洲 Nginx 反代方案可以直接落地；但因为画布是纯前端，长期最优解是让澳洲入口本地提供静态文件，把跨境链路留给 API。

NOW

方案 A · 全量反代

澳洲 Nginx 将 flow.oioi.lat 的所有请求转发到火山云前端源站。

  • 最少改部署结构
  • 源站发布后立即生效
  • 每次 JS/CSS/字体请求都依赖跨境链路
PREFERRED

方案 B · 静态产物落边缘

CI 构建 web/dist，通过 SSH/rsync/对象存储同步到澳洲 Nginx，本地直接提供静态页面。

  • 首屏更稳定，减少跨境请求
  • 可配合 immutable 缓存与原子发布
  • 国内火山云保留为构建/备份或 API 节点
LATER

方案 C · CDN / 多边缘

当海外访问量增长后，再把静态资源迁移到 CDN，澳洲 VPS 仅保留 API 入口与回源策略。

  • 降低单点故障
  • 需要处理缓存失效与发布回滚
  • 不要一开始就引入过多供应商
04 / API CONTRACT

画布如何复用 api.oioi.lat

前端不需要接入新的数据库或新的一套登录系统，只需要把 API 当作外部能力平面，并在运行期配置中注入地址。

FRONTEND

前端边界

  • 新增统一的 apiBaseUrl，默认值为 https://api.oioi.lat。
  • 登录、当前用户、模型列表、模型调用全部经 web/src/services/api/。
  • 组件不直接拼接 URL；统一由 service 层处理鉴权、错误、超时和流式响应。
  • 画布节点、素材索引、生成历史继续写入 IndexedDB/localforage。
API

服务端边界

  • API 继续负责登录、用户身份、模型权限、模型路由和供应商密钥。
  • 对 https://flow.oioi.lat 做精确 CORS allowlist，不使用 *。
  • 生成接口如使用 SSE/WebSocket，需要在边缘 Nginx 保留升级头，并关闭该路径的缓冲。
  • 登录/刷新接口禁止缓存；模型目录可短时间缓存，但要明确失效策略。
01登录02模型目录03模型调用04本地落盘

01登录与会话

浏览器访问 api.oioi.lat/auth/login。若现有 API 使用 Bearer Token，短期 access token 放内存，刷新凭证使用 HttpOnly + Secure cookie；若现有系统已固定使用 cookie，则必须同时配置 SameSite=None; Secure、精确 CORS 和 CSRF 防护。

02模型查看

画布启动后通过 GET /models 获取当前用户可见模型，按能力类型在前端建立轻量缓存。模型目录不是画布数据，不需要写入画布文档；可以在 React Query/Zustand 中维护运行期状态。

03模型调用

节点动作将输入、参考图和模型参数提交给 api.oioi.lat。普通 JSON 用 HTTPS；长任务优先采用“提交任务 → 轮询/事件流”的模式。若是 SSE，边缘层设置 proxy_buffering off 与较长 proxy_read_timeout；若是 WebSocket，转发 Upgrade / Connection。

04结果写入浏览器

调用结果返回后，画布只把节点元数据、提示词、参数、结果引用或用户选择的图片写入 localforage。建议提供“导出画布 JSON / 导入画布 JSON / 清空本地数据”三个入口，避免用户误以为数据已云端同步。

05 / ORIGIN CONTROL

跨境链路怎么做更稳

反向代理本身不是难点，关键是不要把国内源站当成第二个公网入口。

BEST

WireGuard 私网隧道

澳洲与火山云各建立一个 WireGuard peer，Nginx upstream 指向国内节点的隧道 IP，例如 10.90.0.2:8080。

  • 源站端口只对 wg0 开放
  • 链路自带加密，不依赖公网源站端口
  • 便于后续增加第二台源站
PRACTICAL

固定公网 IP + 防火墙白名单

如果暂时不搭隧道，火山云安全组只放行澳洲 VPS 的固定出口 IP，并让边缘到源站继续使用 HTTPS。

  • 上线快，运维成本低
  • 需确保澳洲节点有固定 IP
  • 源站证书/SNI 与健康检查要配置好
NOT FIRST CHOICE

第三方 Tunnel / CDN

可以作为后续容灾或多地域入口，但当前会增加供应商、缓存、域名和故障定位复杂度。

  • 不建议作为第一阶段的必要依赖
  • 先把域名、API 合约与发布流程稳定下来
  • 以后按访问量再引入
06 / DEPLOYMENT

域名与 Nginx 落地

以下配置是结构模板，具体 upstream 地址、证书路径、API 端口和认证头名称要按现有服务调整。

域名DNS 指向公开用途边缘行为
flow.oioi.lat澳洲 VPS 公网 IP画布 SPA静态文件本地提供，或反代至国内 frontend-origin
api.oioi.lat澳洲 VPS 公网 IP登录、用户、模型目录、模型调用反代至国内 api-origin；不缓存认证和生成响应
origin-flow.*不做公网业务入口源站内部标识仅隧道 IP / 澳洲固定 IP 可达
origin-api.*不做公网业务入口API 源站内部标识健康检查与回源使用，不给浏览器使用
# /etc/nginx/conf.d/oioi.conf
# 结构示例：推荐使用 WireGuard 隧道地址作为 upstream

map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

upstream flow_origin {
    server 10.90.0.2:3000;
    keepalive 32;
}

upstream api_origin {
    server 10.90.0.3:8080;
    keepalive 32;
}

server {
    listen 80;
    server_name flow.oioi.lat api.oioi.lat;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name flow.oioi.lat;

    ssl_certificate     /etc/letsencrypt/live/flow.oioi.lat/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/flow.oioi.lat/privkey.pem;

    # 方案 B：dist 已同步到澳洲节点时，直接本地提供
    root /srv/oioi-flow/current;
    index index.html;

    location = /config.js {
        add_header Cache-Control "no-store" always;
        try_files $uri =404;
    }

    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files $uri =404;
    }

    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
    }
}

server {
    listen 443 ssl http2;
    server_name api.oioi.lat;

    ssl_certificate     /etc/letsencrypt/live/api.oioi.lat/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.oioi.lat/privkey.pem;

    location / {
        proxy_pass http://api_origin;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # 长任务 / SSE / WebSocket 按现有协议调整
        proxy_buffering off;
        proxy_read_timeout 300s;
        proxy_send_timeout 60s;
    }
}

如果第一阶段坚持“澳洲 Nginx 全量反代前端”，将 flow.oioi.lat 的本地 root/try_files 替换为 proxy_pass http://flow_origin;，并保留 SPA fallback 策略。

07 / CORS & SECURITY

浏览器与 API 的安全约束

因为页面域名和 API 域名不同，浏览器会将 API 调用视为跨源请求。这个边界要显式设计，不能依赖“本地开发能调用”来判断线上可用。

CORS

推荐的响应策略

Access-Control-Allow-Origin: https://flow.oioi.lat
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type, X-Request-ID
Access-Control-Allow-Credentials: true   # 仅 cookie 会话需要
Vary: Origin

不要使用 Access-Control-Allow-Origin: * 配合凭证；生产环境只允许明确的画布来源，开发环境另列 http://localhost:3100。

SECURITY

必须做的边界

  • 火山云安全组拒绝除隧道/澳洲固定 IP 之外的源站访问。
  • Nginx 日志不要记录 Authorization、refresh token、模型供应商密钥和完整 prompt。
  • 生成接口、登录接口和上传接口分别设置限流与 body size；新增边界值前先确认产品默认值。
  • 加上 HSTS、基础 CSP、X-Content-Type-Options、Referrer-Policy 等响应头。
  • 模型供应商密钥只留在 API 服务端，不放入画布前端。
08 / LOCAL-FIRST

浏览器持久化边界

不接入 new / 服务端数据库并不等于“什么都不设计”。本地数据仍然需要版本、备份和容量边界。

STORE

继续放浏览器

画布节点、节点位置、连接关系、素材索引、提示词、用户选择的模型参数、生成历史引用。

BACKUP

提供手动备份

提供导出 JSON、导入 JSON、清空本地数据。导出内容应包含 schemaVersion，并在导入前校验版本与结构。

LIMIT

明确用户预期

清理浏览器站点数据、切换浏览器或更换设备会导致本地数据不可见；产品文案中不要写成“云端同步”。

09 / ROLLOUT

建议的实施顺序

按照“先打通域名与 API，再优化静态部署”的顺序，能够把风险拆成可验证的小步骤。

01
确认 API 合约列出登录、当前用户、模型列表、模型调用、流式响应、错误格式和 token 刷新方式；先不改画布业务逻辑。
02
建立澳洲边缘入口完成两个域名的 DNS、TLS、Nginx server block、访问日志、健康检查和源站防火墙白名单。
03
画布接入 api.oioi.lat只修改 services/api 与运行期配置；本地存储代码保持不变，先验证跨域登录、模型目录和一次完整生成。
04
将静态文件落到澳洲CI 构建后原子发布到 /srv/oioi-flow/releases/<version>，通过 current 软链接切换，保留上一版用于快速回滚。
05
上线观测与容灾补充边缘 4xx/5xx、回源延迟、API 长连接断开、模型调用失败率和浏览器端本地存储异常的监控。
10 / OPEN RISKS

上线前必须确认的几个问题

这些不是阻塞架构的疑问，但会决定具体配置和体验，建议在实施前逐项定稿。

?
api.oioi.lat 当前是否已经具备跨域登录能力？如果使用 cookie，会影响 SameSite、CORS、CSRF；如果使用 Bearer Token，前端改造通常更直接。
?
模型调用是 JSON、SSE、WebSocket 还是异步任务？这决定 Nginx 是否需要 Upgrade 头、关闭缓冲和拉长读超时。
?
火山云服务器是否有固定公网 IP，澳洲 VPS 是否有固定出口 IP？没有固定地址时优先考虑 WireGuard 或稳定的私网/隧道方案，不要靠频繁改白名单。
?
生成结果是返回临时 URL、对象存储 URL 还是二进制？如果要在浏览器画布中二次导出图片，要同时确认图片资源的 CORS 与有效期。
架构原则： 公网入口集中在澳洲；API 能力独立于画布；源站默认不可直达；画布数据默认留在浏览器；先用最少组件跑通闭环，再按流量引入 CDN 和多地域容灾。
